# Specification: Student Performance PDF Report

**Change ID:** `student-performance-pdf`

## Overview
The system will provide a way for an authenticated user to generate a PDF report that summarizes the academic performance of that user. The PDF is produced by an external Python FastAPI service hosted on Render and stored in Xano. Depending on the storage strategy, the user will receive either:
- **File Resource**: a temporary signed URL to download the PDF, or
- **Base64 fallback**: a protected download endpoint URL that requires user authentication to retrieve the PDF.

The specification describes **what** the system must do, without prescribing concrete XanoScript implementation.

---

## Purpose
Provide an authenticated user with a downloadable PDF summarizing their academic performance, generated by the FastAPI service.

## Requirements

### Requirement: Generate PDF Report
The system **SHALL** generate a PDF report.
#### Scenario: Successful generation
- **WHEN** a valid payload with student name, subjects and tasks is sent to `POST /generate-pdf` with a correct API key,
- **THEN** the service **SHALL** return HTTP 200, `Content‑Type: application/pdf`, and a PDF whose content includes the student name, subject list, task statistics and progress bar.

### Requirement: Handle empty data
The system **SHALL** handle empty payloads.
#### Scenario: No subjects nor tasks
- **WHEN** the payload contains only `student_name`,
- **THEN** the PDF **SHALL** be generated, includes “Nenhuma disciplina cadastrada.” and shows progress 0 %.

### Requirement: Secure access
The system **SHALL** enforce API‑key authentication.
#### Scenario: Invalid API key
- **WHEN** the request header `X‑API‑Key` is missing or incorrect,
- **THEN** the endpoint **SHALL** return HTTP 401.

---

## Functional Requirements

1. **Generate PDF (POST /reports/generate)**
   - Accessible only to authenticated users (`auth = "user"`).
   - When invoked, the endpoint gathers the required data for the requesting user, builds a payload, and forwards it to the FastAPI service via a POST request to the URL defined in the environment variable `PDF_API_URL`.
   - The FastAPI service returns a PDF binary (`content-type: application/pdf`).
   - The PDF is stored in Xano using the *Create File Resource → Create Attachment Metadata* workflow (or, if private file resources are unavailable, stored as a Base64 string in a fallback table).
   - The endpoint stores **only** the `file_resource_id`, `owner_id` and `created_at` in the `reports` (or fallback) table. It **does not** store the signed URL permanently.
   - **Response varies by storage strategy:**
     - **File Resource:** returns `{ "report_id": <id>, "url": "https://xano.com/signed/..." }` where `url` is a freshly‑generated temporary signed URL.
     - **Base64 fallback:** returns `{ "report_id": <id>, "download_url": "/reports/<report_id>/download" }` – a URL pointing to the protected download endpoint.
   - **Data‑absence rule:** If the user has no subjects or tasks, the endpoint must still succeed, generating a PDF with empty sections and a progress of 0 %. It must **not** return HTTP 400. Real communication or storage failures may still result in appropriate error responses such as HTTP 502.

2. **Download PDF (GET /reports/{report_id}/download)**
   - Protected endpoint (`auth = "user"`).
   - Validates that `$auth.id` matches the `owner_id` of the requested report record.
   - **File Resource strategy:** If the stored `file_resource_id` can be used to produce a signed URL, a fresh temporary signed URL is created on‑demand and returned in JSON (`{ "url": "..." }`).
   - **Base64 fallback strategy:** When the PDF is stored as a Base64 string, the endpoint decodes the data and returns the binary PDF with `Content-Type: application/pdf` and `Content‑Disposition: attachment; filename="report.pdf"`.
   - The returned URL (when applicable) is **temporary**; any holder can download the PDF while it remains valid.

## Data Model (minimum required fields)
- **reports** table (or `pdf_reports` fallback) must contain at least:
  - `id` – primary key.
  - `owner_id` – reference to `user.id` (the authenticated user who requested the report).
  - `file_resource_id` – ID of the Xano File Resource (when private storage is available).
  - `created_at` – timestamp of report generation.
  - *(Optional)* `base64_pdf` – Base64‑encoded PDF string, used only when private file resources are unavailable.

---

## Security Considerations
- **Signed URL:** The URL is temporary; any holder can download the PDF while it remains valid. The system does not store it permanently.
- **Endpoint Protection:** Only the authenticated owner may invoke `/reports/generate` and `/reports/{report_id}/download`. Ownership is enforced by comparing `$auth.id` with `owner_id`.
- **Data Isolation:** All queries that fetch subjects or tasks must include `where = $db.subjects.user_id == $auth.id` (or the equivalent list‑based filter for tasks).

---

## Validation Rules
- The generate endpoint must succeed for an authenticated user even when the user has no subjects or tasks; the resulting PDF will show empty sections and a progress of 0 % (see Data‑absence rule).
- The payload sent to the FastAPI service must include all required fields; missing optional `hours` should be omitted rather than set to null.
- The download endpoint must generate a fresh signed URL on‑demand when the storage strategy permits it, or return the decoded binary PDF for the Base64 fallback.

---

## Non‑Functional Requirements (derived from Non‑Goals)
- **Internationalization:** PDF will be generated only in the default language (no i18n support).
- **Report Length:** Single‑page layout; no multi‑page pagination.
- **Graphics:** Only plain text/tables; no charts or advanced graphics.
- **Scheduling:** Reports are generated on demand; no automatic or scheduled generation.
- **FlutterFlow UI:** No changes to the FlutterFlow interface are part of this change.

---

## Acceptance Criteria (reiterated)
- All functional requirements above are met.
- The signed URL or the binary download behavior follows the selected storage strategy (temporary signed URL for File Resource, protected binary download for Base64 fallback).
- Errors are returned with the correct HTTP status codes.
- The storage‑strategy decision is documented and implemented according to the verified Xano capabilities.
